# Agent 경로 수정 및 오프라인 검증 결과

상태: 코드 수정·오프라인 회귀 검사 완료. 100문항 실호출 평가는 준비만 했으며 실행하지 않음.

## 수정 범위

작업 위치는 바탕화면 pension이다. 기존 미커밋 변경을 포함한 현재 작업물을 기반으로 수정했다.
원본 PDF, 추출 JSON/CSV, 데이터베이스, 벡터 인덱스를 다시 생성하거나 덮어쓰지 않았다.
커밋·푸시는 하지 않았다. API 키는 코드에 넣지 않았으며 외부 연결을 차단한 검사만 수행했다.

## 실제 변경

1. API 진입 경로 통일
   - api/server.py → runtime.py로 연결했다.
   - Fast Path가 실패하면 Planner로 이동한다. Planner 실패를 기존 제도 RAG로 대체하던 경로는 제거했다.
   - 도구/자료 미확인과 실행 장애를 구분한다. 실행 장애를 '해당 상품 없음'으로 반환하지 않는다.

2. 상품 식별 및 조건 보존
   - Anchor와 상품 조회가 같은 resolver를 사용한다.
   - '장점과 단점'의 접속사를 상품 비교로 오인하지 않는다.
   - 없는 초장기 상품을 중장기 상품으로 대체하지 않는다.
   - 전체 의미를 해석한 질문만 Fast Path로 보낸다. 미해석 조건이 있으면 Planner가 처리한다.
   - 3등급 이하를 eq 3으로 좁히거나, 원문과 연결되지 않은 필터를 삭제한 채 실행하지 않는다.

3. 공통 정형 Repository
   - FACT/FILTER/COMPARE가 동일한 클래스 단위 조회를 사용한다.
   - 가입대상·보수·수익률 조건은 같은 클래스에서 동시에 만족해야 한다.
   - 국공채를 포함한 채권형 매핑과 원 단위 AUM을 사용한다.
   - 조회 개수를 임의로 5개로 제한하지 않는다. 명시적 개수 제한은 상품 단위이며 해당 클래스는 보존한다.
   - IRP/DC/DB 가입이 명시되지 않은 퇴직연금 클래스는 확정 가입으로 취급하지 않는다.
   - 요약표와 상세표의 같은 지표가 충돌하면 양쪽 값을 보존하고 확정 필터 값으로 쓰지 않는다.
   - 기준일이 없는 수익률/AUM에 날짜를 만들지 않는다. 클래스·기간·기준일 차이를 표시한다.

4. Task 실행 및 계산
   - Task 순서와 depends_on을 실행한다. 선행 Task 실패 시 종속 Task를 건너뛴다.
   - FACT/COMPARE는 입력에 지정된 지표·클래스를 사용한다. 질문 키워드를 다시 읽어 요구를 덮어쓰지 않는다.
   - 각 Task에 지정한 상품 범위를 전체 Anchor 상품으로 덮어쓰지 않는다.
   - 납입액과 소득을 등장 순서가 아니라 문장 속 역할로 연결한다.
   - 검증된 단일 계좌 기본 세액공제만 계산기에 연결했다. 복수 계좌 합산·특례·다른 세목은 문서 근거가 필요하다.

5. RAG/Context
   - Planner의 RISK_NARRATIVE 등 FactType이 실제 검색·섹션 우선순위에 반영된다.
   - Task별 검색 결과를 기본 3개로 제한하되 후보 검색은 더 넓게 한다.
   - 같은 페이지의 다른 청크를 버리지 않고, 본문을 700자에서 조용히 자르지 않는다.
   - Task/상품별로 Context 예산을 나누고, 제외된 근거 및 Task를 기록한다.
   - flat 인덱스/모델의 반복 로딩을 파일 버전 기반 캐시로 줄였다. 실제 검색 백엔드를 메타데이터에 기록한다.

6. 검증/재처리/관측
   - 전역 숫자 집합만 확인하지 않고 인용별 숫자와 typed 지표 값을 대조한다.
   - 고위험 답변 및 문서 서술 답변은 의미 검증 LLM을 거친다. Python 검사를 의미 검증으로 과장하지 않는다.
   - 오류별 재처리는 전체 요청당 1회다. 오류 Task와 추가 검색문을 전달하고 재작성에는 이전 답변도 전달한다.
   - 재실패 시 검증되지 않은 RAG 원문을 '검증 통과한 답변'으로 나열하지 않는다.
   - 최초 검증·재검증 이력, Task 상태, 단계별 LLM 호출, HTTP 시도, 실제 usage와 추정 토큰을 구분해 기록한다.
   - 캐시는 5분 TTL 및 DB/프롬프트/청크 버전 변경으로 무효화한다.

## 비용상 바뀐 점

- 명확한 정형 조회/필터/비교: LLM 0회.
- Planner가 정형 Task만 결정: 일반적으로 Planner 1회, 이후 템플릿.
- 문서 서술: 정상 경로 Planner + 생성 + 의미 검증으로 일반적으로 3회.
- 재처리가 필요하면 생성 및 최종 검증이 추가될 수 있다. 1회 재처리와 HTTP 재시도는 별도 집계한다.
- 이것은 실제 비용을 측정한 수치가 아니라 호출 경로 설명이다. 이번 작업의 HCX 실호출은 0회다.

## 오프라인 검사

- 새 회귀 검사 34개 통과.
- 기존 Agent 검사 81개 중 80개 통과, 기존 등록된 기대 실패 1개 유지.
- 기대 실패는 기존 문서 helper에서 '중도' 없이 '해지 시'라고 묻는 표현의 검색 품질 한계다.
- 기존 기대값 중 잘못된 의미(검증 안 된 원문을 '검증 통과'로 안내, 표를 가짜 문서명으로 인용 등)는 새 계약에 맞게 수정했다.
- 예전 API fallback을 기대하던 테스트와 현재 프로덕션 경로 검사를 구분했다. 새 검사에는 실제 API 진입·legacy 우회 차단 검사가 있다.
- scripts/check_agent_offline.py는 프로젝트 import 전에 socket 연결을 차단한다. 아래 검사는 100문항 평가와 별개다.

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/check_agent_offline.py test_agent_v2.py
.\.venv\Scripts\python.exe -X utf8 scripts/check_agent_offline.py test_pipeline_contracts.py
```

## 아직 검증하지 않은 것과 남은 한계

1. 새 프롬프트의 실제 HCX 출력·첫 응답 통과율·질문별 답변 품질·실제 토큰 비용은 아직 검증하지 않았다.
2. 현재 flat 검색은 TF-IDF/SVD이며 사전학습 의미 임베딩으로 교체하지 않았다. 다양한 표현의 실제 검색 성능은 평가가 필요하다.
3. 원문/추출 데이터의 빠진 기준일과 가입대상을 새로 만들어 채우지 않았다. 따라서 일부 후보는 미확인으로 남는다.
4. 기존 상품코드/중복 문서 매핑은 유지했다. 값이 같다는 이유만으로 서로 다른 상품코드를 새로 합치지 않았다.
5. 단순 정형 컴파일러가 모든 자연어 표현을 지원하는 것은 아니다. 미해석 표현은 Planner로 보내는 것이 의도한 동작이다.
6. Python과 검증 LLM이 모두 통과해도 실제 품질의 완전한 보장은 아니다. 100문항은 답변/근거를 별도로 판정해야 한다.

## 준비된 100문항

tests/evaluation_100_review_v2.json에 10유형 × 10문항을 준비했다.

상품 식별 / 단일 정형 / 조건 필터 / 비교·순위 / 상품 서술·복합 / 제도 / 세제·계산 / 절차·대응 / 추천·정보 부족 / 안전·부정 전제·누락.

각 문항에는 확인할 계약이 포함되어 있다. 외부 호출로 얻지 않은 답을 정답처럼 저장하지 않았다.
현재 status는 PREPARED_NOT_EXECUTED이며 실행한 문항은 0개다.
다음 단계는 사용자 확인 후 실제 운영 경로로 HCX가 필요한 질문을 호출하고, 질문·답변·근거·검증 이력·토큰을 함께 보고하는 것이다.
